## 1. Goal

This plan pairs DuckDB with ShelfDB on the 50 high-variance fraud cases. The approved documents give case names, not Structured Query Language (SQL) text. This plan records the names only. It does not invent SQL. It does not install software and does not run a benchmark.

## 2. Concept definitions

- **DuckDB:** an embedded columnar database that runs SQL in one process.
- **ShelfDB:** a sheaf database that stores answers in binary cellular storage sections.
- **High-variance case:** a recorded test case that changes solver or filter inputs.
- **SQL:** the standard language for relational queries.
- **Gate:** an automatic comparison of an engine result with a truth value.

## 11. Acceptance gate

1. Make sure that one container runs at a time.
2. Make sure that `docker inspect` reports one central processing unit and 2 gigabytes of memory.
3. Run all 50 identifiers TC-01 through TC-50. Do not drop a case.
4. Make sure that each matched row count equals the count in the source document.
5. Make sure that each result matches the recorded checksum.
6. Keep the warm-up pass outside the timed set.
7. Record the five loss cases as losses. Do not hide them.
8. Write all evidence files from Table 7.
9. Stop the container and wait three minutes before the next pair.
10. Record `unsupported` with the named cause if a case cannot run. Do not write a fake result.
