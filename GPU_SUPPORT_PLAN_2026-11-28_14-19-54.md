## 1. Goal

This plan adds GPU support for database mathematics. It uses Google Colab and Kaggle with an NVIDIA T4 GPU. It makes no code change now. It runs no GPU job now. The user must approve each node before execution.

## 2. What the GPU tier will do

The GPU tier will accelerate these database operations:

1. Sparse Sheaf Laplacian products.
2. Chebyshev and conjugate gradient iterations.
3. Batch column scans and predicate masks.
4. Fiber join aggregation.
5. Graph traversal kernels.
6. Fingerprint and checksum batch work.

The local AMD Radeon integrated graphics unit is outside this phase. It has no mature database compute stack in this project. Use cloud T4 GPUs for measured work.

## 4. G-01 and G-02 local design

1. Define a `GpuKernel` port in a new Rust file.
2. Keep the current central processing unit kernel as the declared fallback.
3. Report `Unsupported` when no CUDA device is present.
4. Do not link CUDA into the main workspace yet.
5. Put the prototype in a separate crate or branch.
6. Use one small fixture of 10,000 cells.
7. Compare the Laplacian product element by element.
8. State tolerance before the run. Use relative error 1e-5.
9. Record the command and output in the evidence folder.

## 5. Colab API procedure

This procedure uses the official Colab API. The API manages runtimes. A runtime is a managed Jupyter server.

### 5.1 One-time setup

1. Create a Google Cloud project.
2. Enable the Colab API in that project.
3. Configure OAuth 2.0 credentials.
4. Store the client ID and secret outside the repository.
5. Install the Google client library for Python.
6. Make sure that the account can request a T4 runtimespec.
7. Record the subscription tier. Free or paid status can change eligibility.

### 5.2 Discover a T4 runtime

1. Call `getSubscription`.
2. Call `listRuntimeSpecs`.
3. Select a spec with variant `VARIANT_GPU`, accelerator `T4`, and shape `SHAPE_STANDARD`.
4. If no T4 spec is eligible, stop. Record `unsupported` with the named cause.
5. Do not substitute an A100 or H100 without approval.

### 5.3 Create and use the runtime

1. Generate a new UUID for `requestId`.
2. Call `POST https://colaboratory.googleapis.com/v1beta/runtimes`.
3. Wait for the operation to finish.
4. Call `get` on the runtime.
5. Read `connectionInfo.url` and `connectionInfo.token`.
6. Connect to the Jupyter server with that token.
7. Open one session with a stable name.
8. Upload the prototype file and the small fixture through HTTP.
9. Do not send large files as base64 text through a model call.
10. Run a device check. The output must name Tesla T4.
11. Run the kernel parity fixture.
12. Save stdout, stderr, and the result artifact.
13. Close the session.
14. Delete the runtime when the run is done.

### 5.4 Colab execution rules

1. Use one execution call at a time in one session.
2. Give each execution a new UUID `executionId`.
3. A call stops after 600 seconds. Repeat the same call with the same identifier after a timeout.
4. Keep data under 100 MB for the first run.
5. Do not store tokens in the repository.

## 6. Kaggle API procedure

This procedure uses the Kaggle command line interface. A push uploads a notebook and starts a run.

### 6.1 One-time setup

1. Create a Kaggle account.
2. Generate an API token from the account settings page.
3. Store the token outside the repository.
4. Install the Kaggle command line interface.
5. Make sure that `kaggle --version` works.
6. Record the account GPU entitlement.

### 6.2 Notebook package

Create one notebook folder with these two files:

```text
gpu_t4_parity/
  kernel-metadata.json
  gpu_t4_parity.ipynb
```

Use this metadata shape:

```json
{
  "id": "<username>/sheafdb-gpu-t4-parity",
  "title": "SheafDB GPU T4 Parity",
  "code_file": "gpu_t4_parity.ipynb",
  "language": "python",
  "kernel_type": "notebook",
  "is_private": "true",
  "enable_gpu": "true",
  "enable_internet": "false",
  "machine_shape": "NvidiaTeslaT4",
  "dataset_sources": [],
  "competition_sources": [],
  "kernel_sources": [],
  "model_sources": []
}
```

Replace `<username>` with the real account name before a run.

### 6.3 Run steps

1. Write the notebook. Print the device name in the first cell.
2. Upload the small fixture as a Kaggle dataset or place it in the notebook package.
3. Run `kaggle kernels push -p gpu_t4_parity`.
4. Poll with `kaggle kernels status <username>/sheafdb-gpu-t4-parity`.
5. Stop polling when the status is `complete` or `failed`.
6. Fetch output with `kaggle kernels output <username>/sheafdb-gpu-t4-parity -p results/kaggle_t4`.
7. Make sure that the device line names Tesla T4.
8. If the device line names another GPU, record a mismatch. Do not claim a T4 result.
9. Compare the result checksum with the local CPU fixture.
10. Record the notebook URL and run time in the evidence file.

## 8. Acceptance gates

1. CPU and GPU results match at relative error 1e-5.
2. Both cloud runs report NVIDIA T4.
3. No token or secret enters Git.
4. Each run writes a checked result artifact.
5. The timing table names the data set, query, device, and source file.
6. A failed gate records `unsupported` with a named cause.
